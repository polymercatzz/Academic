# เตรียมถาม–ตอบ (15 นาที)

หลักการตอบ: ตอบประโยคแรกให้ตรงคำถาม → ให้เหตุผล 1–2 ข้อ → ถ้ามีสไลด์สำรองให้เปิดประกอบ
ถ้าไม่รู้: ยอมรับตรง ๆ แล้วบอกว่าจะจัดการในเทอม 2 อย่างไร
แบ่งกันตอบ: P = สถาปัตยกรรม/อัลกอริทึม/ฐานข้อมูล, I = ความต้องการ/ผู้ใช้/หน้าจอ/การทดสอบ (ปรับได้)

## ความแปลกใหม่และความจำเป็น

| คำถามที่น่าจะเจอ | แนวตอบ (เติมให้ครบ) | สไลด์ |
|---|---|---|
| ต่างจาก SchoolBright ยังไง ทำไมโรงเรียนไม่ใช้ของที่มีอยู่ | SchoolBright ไม่พบการจัดตาราง/ตรวจชน, ไม่มีการกำหนดสัดส่วนคะแนน+นำเข้าไฟล์ครบ; เราทำครบในระบบเดียวและข้อมูลไหลต่อกัน | 4, 5 |
| เก็บความต้องการจากผู้ใช้จริงไหม | ศึกษาระบบเดิม + หลักสูตรแกนกลาง + แนวปฏิบัติการวัดผล, Persona สร้างจากการวิเคราะห์; ยอมรับข้อจำกัด และมีแผนให้ผู้ใช้ทดลองต้นแบบเดือนที่ 1 ของเทอม 2 | 3, 17 |
| แต่ละโรงเรียนทำไม่เหมือนกัน รองรับยังไง | ยึดส่วนกลางที่ทุกโรงเรียนใช้ร่วม ส่วนที่ต่าง (สัดส่วนคะแนน, โครงสร้างเวลาเรียน) ให้โรงเรียนตั้งค่าเอง | 17 |

## การออกแบบและเทคนิค

| คำถาม | แนวตอบ | สไลด์ |
|---|---|---|
| อัลกอริทึมจัดตารางคืออะไร ทำไมเลือกแบบนี้ | heuristic จัดจากยากไปง่าย + ให้คะแนน soft constraint; ต้องเตรียมเหตุผลว่าทำไมไม่ใช้ GA / CP-SAT / ILP และ worst case | 11, B5 |
| ถ้าจัดอัตโนมัติไม่ได้ครบทุกคาบ? | คาบที่วางไม่ได้แจ้งให้ฝ่ายวิชาการจัดเองพร้อมเหตุผล (เช่น ครูติดสอนทุกช่อง) | 11, 12 |
| เป้า 40 ห้องภายใน 5 นาที มาจากไหน | (เติม) ขนาดโรงเรียนอ้างอิง + จะยืนยันด้วย Load test | 18, B6 |
| ทำไมเป็น Microservice ไม่ใช่ Monolith | ทำร่วมกับอีกทีม (Service B) แยกความรับผิดชอบ, deploy อิสระ; ยอมรับต้นทุนเรื่อง integration | 7 |
| ทำไมต้อง Celery/Redis | งานจัดตาราง/คำนวณเกรดทั้งระดับชั้นใช้เวลานาน ไม่ให้ request ค้าง แจ้งสถานะเมื่อเสร็จ | 7, 11 |
| 58 ตาราง เยอะไปไหม normalize ถึงไหน | (เติม) กลุ่มตาราง + ระดับ normal form + เหตุที่แยก | 10, B4 |
| ข้อมูลซิงก์กับ Service B อย่างไร ถ้า B ล่ม? | (เติม) ข้อมูลหลักที่ดึงมา, การ cache, แผน mock ตามสัญญา API | 7, B8 |
| ทำไมตารางที่เผยแพร่แล้วแก้ไม่ได้ | ป้องกันข้อมูลเช็คชื่อที่ผูกกับคาบเสียความสอดคล้อง; ต้องผ่านคำร้อง/สร้างฉบับใหม่ | 10 |
| ครูสองคนแก้คะแนนพร้อมกัน? | (เติม) การ lock / optimistic concurrency; อยู่ในแผน Load test "ไม่เกิด Data Conflict" | B6 |
| ความปลอดภัย/สิทธิ์ | ตรวจ Token + บทบาทที่ gateway และ service, บัญชีผู้ใช้อยู่ที่ Service B | 7 |

## สถานะงานและแผน

| คำถาม | แนวตอบ | สไลด์ |
|---|---|---|
| ทำไมยังไม่มี backend | ขอบเขตเทอม 1 คือวิเคราะห์–ออกแบบ–ต้นแบบ ตามแผน 1.4; ความคืบหน้า 47.5% | 16 |
| เทอม 2 ทำทันไหม | แผน 4 เดือน, ล็อกขอบเขตหลังเดือน 1, เรียงพัฒนาตาม data flow, แผนสำรองเลื่อนฟีเจอร์รอง | 17, B7 |
| ใช้ AI แล้วผลงานเป็นของใครแค่ไหน | คนตัดสินใจและตรวจทุกขั้น AI ร่าง, บันทึกการตัดสินใจด้านการออกแบบเป็นหลักฐาน | 15 |
| ทดสอบยังไงว่าเกรดคำนวณถูก | Unit test เทียบกับการคำนวณมือ 100% ทุกกรณี | 13, B6 |

## คำถามเชิงความรู้พื้นฐาน (ทบทวนให้พร้อม)

- เกณฑ์ มส 80% / ผลการเรียน ร, มส, มผ / การสอบซ่อมได้สูงสุดเกรด 1
- นิยาม Hard vs Soft constraint, timetabling เป็นปัญหา NP-hard
- REST vs อื่น ๆ, ORM คืออะไร, Normalization 1NF–3NF
