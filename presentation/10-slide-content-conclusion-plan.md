## H1. สรุปผลภาคเรียนที่ 1

**หัวสไลด์:** เทอม 1 ออกแบบครบทั้ง 5 ระบบตามวัตถุประสงค์ เหลือพัฒนาจริงในเทอม 2

**บนสไลด์**

ซ้าย (จุดเด่นของหน้า): ตารางวัตถุประสงค์ 5 ข้อ (เล่มข้อ 1.2 ข้อละ 1 ระบบ)

| วัตถุประสงค์ | ออกแบบ | ต้นแบบหน้าจอ | พัฒนาจริง |
|---|:-:|:-:|:-:|
| 1 ระบบจัดการหลักสูตร | ✓ | ✓ | เทอม 2 |
| 2 ระบบจัดตารางสอน | ✓ | ✓ | เทอม 2 |
| 3 ระบบเช็คชื่อ | ✓ | ✓ | เทอม 2 |
| 4 ระบบบันทึกคะแนน | ✓ | ✓ | เทอม 2 |
| 5 ระบบออกรายงาน | ✓ | ✓ | เทอม 2 |

ขวา: ตัวเลขใหญ่ **47.5%** · ใต้ตัวเลข: ความคืบหน้ารวม · หลักฐาน 3 บรรทัด: **26** use case · **58** ตารางฐานข้อมูล · **74** หน้าจอต้นแบบ

**ภาพ:** ไม่มี

**พูด**
- 47.5% เป็นไปตามแผน งาน Backend และการทดสอบ (น้ำหนักรวม 45%) วางไว้ในเทอม 2 ตั้งแต่ต้น
- ถ้าถูกถามรายละเอียด (ตาราง 5.1): วิเคราะห์และออกแบบ 98% · UX/UI 90% · Back-end 0% · ทดสอบ 0% · เล่มและนำเสนอ 50%
- ตัวเลขหลักฐาน: 26 use case (บทที่ 3) · 58 ตาราง (ER/Data Dictionary) · 74 หน้าจอ (รูปในบทที่ 4)

## H2. ปัญหาที่เจอและวิธีแก้

**หัวสไลด์:** ขอบเขตเปลี่ยนบ่อยและยังไม่มีข้อมูลจริง ทีมจึงบันทึกการตัดสินใจและยึดหลักสูตรแกนกลาง

**บนสไลด์** (3 แถว ปัญหา → วิธีแก้)

| ปัญหา | วิธีแก้ |
|---|---|
| ขอบเขตเปลี่ยนบ่อย ต้องกลับไปแก้ use case, Activity และ ER | บันทึกการตัดสินใจทุกครั้งที่ขอบเขตเปลี่ยน แก้แผนภาพไปพร้อมกัน · **ล็อกขอบเขตหลังเดือนที่ 1 ของเทอม 2** |
| ข้อมูลจำลองยังละเอียดไม่พอ | ทำข้อมูลทดสอบชุดเดียวกันทุกระบบย่อย ให้จำนวนห้อง ครู รายวิชา ใกล้เคียงโรงเรียนจริง |
| เก็บข้อมูลจากผู้ใช้จริงยาก แต่ละโรงเรียนทำไม่เหมือนกัน | ยึดหลักสูตรแกนกลางและแนวปฏิบัติการวัดผล · ส่วนที่ต่างกัน เช่น สัดส่วนคะแนน โครงสร้างเวลา ให้โรงเรียนตั้งค่าเอง |

**ภาพ:** ไม่มี

**พูด:** ทั้ง 3 ข้อมาจากข้อ 5.2.2 · ข้อ 3 เป็นเหตุผลที่ระบบให้ตั้งค่าโครงสร้างคะแนนและโครงสร้างเวลาเองได้ (เชื่อมกับ F1 และ D1)

## H3. งานที่ยกไปภาคเรียนที่ 2

**หัวสไลด์:** ยังเหลือ Backend ฐานข้อมูล 4 ตาราง และข้อตกลง API กับ Service B

**บนสไลด์** (3 การ์ด)

| ตาราง DB ที่ยังไม่ได้ออกแบบ 4 ตาราง | ข้อตกลง API กับ Service B | ส่วนที่ต้องพัฒนาจริง |
|---|---|---|
| สถานะงานเบื้องหลัง · ประวัติการนำเข้าไฟล์ · ประวัติการแก้หลักสูตรและรายวิชา · ประวัติการส่งออกเอกสาร | รายละเอียดแต่ละ endpoint กับระบบงานทะเบียนและ IAM | ต้นแบบเป็นหน้าจอกับข้อมูลจำลอง ยังไม่มี Backend ฐานข้อมูล และงานเบื้องหลังจริง |
| ทำในเดือนที่ 1 พร้อมล็อกขอบเขต | กำหนดร่วมกับอีกทีมในเดือนที่ 1 | พัฒนาตามแผน H5 |

**ภาพ:** ไม่มี

**พูด:** มาจากข้อ 5.2.3 · ทั้ง 3 ข้อมีกำหนดเวลาในตาราง 5.3 แล้ว

## H4. ข้อเสนอแนะ

**หัวสไลด์:** ระบบควรถูกทดสอบกับครูและข้อมูลจริงก่อนขยายไปงานส่วนอื่น

**บนสไลด์** (4 ข้อ ข้อละ 1 บรรทัด + ที่มาตัวเล็ก)

1. **สัมภาษณ์ครูจริงก่อนล็อกขอบเขต** · Persona ตอนนี้สร้างจากการวิเคราะห์ระบบเดิม ยังไม่ได้มาจากการสัมภาษณ์ (3.1.1, 5.2.2 ข้อ 3)
2. **ทดสอบกับข้อมูลขนาดเท่าโรงเรียนจริง** · โดยเฉพาะการจัดตารางอัตโนมัติ (5.2.2 ข้อ 2, ตาราง 5.4)
3. **ปรับหน้าเช็คชื่อให้ใช้บนมือถือได้เต็มที่** · ครูเช็คชื่อทุกคาบ แต่ตอนนี้ใช้บนมือถือได้บางส่วน (ตารางเปรียบเทียบระบบ บทที่ 2)
4. **ต่อยอดงานนอกขอบเขต** · ระบบแจ้งลาของนักเรียน · ความประพฤติ · งานบุคลากร (ขอบเขต บทที่ 1)

**ภาพ:** ไม่มี

**พูด**
- ⚠ เล่มไม่มีหัวข้อข้อเสนอแนะ ทุกข้อในสไลด์นี้มาจากข้อจำกัดที่เล่มเขียนไว้เอง · ถ้าจะใช้สไลด์นี้ ควรเพิ่มหัวข้อ 5.4 ข้อเสนอแนะในเล่มให้ตรงกัน
- ข้อ 1–2 ทำได้ภายในเทอม 2 (อยู่ในแผนแล้วบางส่วน) · ข้อ 3–4 เป็นงานหลังจบโครงงาน

## H5. แผนการพัฒนาภาคเรียนที่ 2

**หัวสไลด์:** พัฒนาทีละระบบตามลำดับที่ข้อมูลส่งต่อกัน ภายใน 4 เดือน

**บนสไลด์**

บน: ลำดับการพัฒนา (ลูกศรแถวเดียว ตรงกับสไลด์การไหลของข้อมูล B5)

```
หลักสูตร → ตารางสอน → เช็คชื่อ → บันทึกคะแนน → รายงาน
```

ล่าง: การ์ด 4 เดือน เรียงซ้ายไปขวา (ตาราง 5.3)

| เดือน 1 · เตรียมและล็อกขอบเขต | เดือน 2 · พัฒนาระบบหลัก | เดือน 3 · รายงานและทดสอบรวม | เดือน 4 · ทดสอบกับผู้ใช้ |
|---|---|---|---|
| • ยืนยันขอบเขต<br>• ให้ผู้ใช้ลองต้นแบบ<br>• ข้อตกลง API<br>• ติดตั้งระบบ + ฐานข้อมูล<br>• ระบบหลักสูตร + Service B | • ตารางสอน<br>• เช็คชื่อ<br>• บันทึกคะแนน | • ระบบออกรายงาน<br>• Integration Test<br>• System + Load Test | • System + Load Test (ต่อ)<br>• UAT แล้วปรับแก้<br>• ปรับเล่ม เตรียมนำเสนอ |

แถบล่าง: **ทำตลอดเทอม:** Unit Test และบูรณาการกับกลุ่มอื่นทุก 2 สัปดาห์ (เดือน 1–3) · นำเสนออาจารย์ที่ปรึกษาทุก 2 สัปดาห์

**ภาพ:** ไม่มี (การ์ด 4 ใบเป็นองค์ประกอบหลัก)

**พูด**
- หลักการ 6 ข้อจาก 5.3.1: ล็อกขอบเขตหลังเดือนที่ 1 · พัฒนาตามลำดับข้อมูล · ใช้ต้นแบบเป็นข้อกำหนดหน้าจอ และใช้ Activity กับกฎข้อ 3.5 เป็นข้อกำหนดการประมวลผล · ให้ผู้ใช้ลองต้นแบบก่อนพัฒนาจริง · กรณีทดสอบครอบคลุมทุก use case · ทำ Unit Test ไปพร้อมกับพัฒนา
- เรียงตามลำดับข้อมูลเพราะแต่ละระบบใช้ข้อมูลจากระบบก่อนหน้า เช่น เช็คชื่อต้องมีตารางที่เผยแพร่แล้ว

## H6. แผนการทดสอบ

**หัวสไลด์:** ทดสอบ 5 ระดับ ตั้งแต่ Unit Test จนถึงให้ครูใช้จริง แต่ละระดับมีเป้าหมายที่วัดได้

**บนสไลด์** (ตาราง 5.2 ย่อ)

| ระดับ | ทดสอบอะไร | เป้าหมาย |
|---|---|---|
| Unit | คำนวณคะแนนและเกรด · จำกัดผลสอบซ่อม · เวลาเรียนและ มส · ตรวจการชน | ผ่านทุกกรณี ตรงกับคำนวณมือ **100%** |
| Integration | API ระหว่างระบบย่อย · สิทธิ์และข้อมูลหลักจาก Service B · งานเบื้องหลัง Redis/Celery | ข้อมูลตรงต้นทาง · เห็นเฉพาะตามสิทธิ์ · งานเบื้องหลังแจ้งสถานะได้ |
| System | ทั้ง 26 use case ตาม Activity Diagram | ทำงานตาม Basic Flow และแสดงข้อความตาม Alternative/Exception Flow |
| Load | ครูหลายคนบันทึกพร้อมกัน · จัดตารางอัตโนมัติ · คำนวณผลทั้งระดับชั้น | ไม่เกิด Data Conflict · **จัดตาราง 40 ห้อง ≤ 5 นาที** · **คำนวณผลทั้งระดับชั้น ≤ 1 นาที** |
| UAT | ครูทำงานตามขั้นตอนของ Persona ทั้ง 2 คน | ทำงานได้ครบด้วยตนเอง · บันทึกข้อเสนอแนะ |

ล่าง 1 บรรทัด: **ทุกระดับใช้ข้อมูลทดสอบชุดเดียวกัน**

**ภาพ:** ไม่มี (ตารางเป็นองค์ประกอบหลัก) · ตัวเลขเป้าหมาย 3 ตัวทำตัวหนา

**พูด**
- Unit Test ทำไปพร้อมกับพัฒนา ส่วนระดับอื่นทำตามช่วงเวลาใน H5
- ก่อนเริ่มพัฒนาจริง ให้ผู้ใช้ลองต้นแบบหน้าจอก่อน (5.3.1 ข้อ 4)

## H7. ความเสี่ยงและแผนรองรับ

**หัวสไลด์:** ความเสี่ยงหลัก 5 ข้อมีแผนสำรองแล้ว ข้อที่กระทบมากที่สุดคือระบบของกลุ่มอื่นเสร็จไม่ทัน

**บนสไลด์** (ตาราง 5.4)

| ความเสี่ยง | แผนรองรับ |
|---|---|
| ระบบของกลุ่มอื่นเสร็จไม่ทัน | ใช้ระบบจำลองที่ตอบตามข้อตกลง API ไปก่อน แล้วเชื่อมจริงเมื่อพร้อม |
| พัฒนาไม่ทันตามแผน | ทำระบบหลักก่อน (ตารางสอน บันทึกคะแนน เช็คชื่อ) · จัดอัตโนมัติแบบกำหนดเงื่อนไขและรายงานบางประเภทเป็นงานเสริม |
| หาผู้ใช้จริงมาทำ UAT ไม่ได้ | ให้อาจารย์หรือเพื่อนสวมบทครูตาม Persona |
| Service B เปลี่ยนวิธีตรวจสิทธิ์หรือรูปแบบข้อมูล | ตกลง API ตั้งแต่เดือนที่ 1 · แยกส่วนที่เชื่อมระบบอื่นไว้ที่เดียว แก้จุดเดียว |
| จัดตารางอัตโนมัติช้ากับข้อมูลจริง | ทดสอบกับข้อมูลขนาดเท่าโรงเรียนจริงตั้งแต่ต้น · ให้เลือกจัดเฉพาะครูหรือห้องที่ต้องการได้ |

**ภาพ:** ไม่มี

**พูด:** ความเสี่ยงข้อ 1 และ 4 เกี่ยวกับอีกทีม จึงต้องตกลง API ในเดือนที่ 1 ตาม H5

## H8. สิ่งที่จะส่งมอบเมื่อจบภาคเรียนที่ 2

**หัวสไลด์:** เมื่อจบภาคเรียนที่ 2 ระบบทั้ง 5 ระบบย่อยจะทำงานจริงและผ่านเป้าหมายการทดสอบทั้ง 5 ระดับ

**บนสไลด์** (3 คอลัมน์: ส่งอะไร · เมื่อไร · วัดอย่างไร)

| ส่งมอบ | เมื่อไร | วัดอย่างไร |
|---|---|---|
| ขอบเขตที่ล็อกแล้ว + ข้อตกลง API กับ Service B | เดือน 1 | เอกสารข้อตกลงที่ทั้งสองทีมยืนยัน |
| ระบบหลักสูตร ตารางสอน เช็คชื่อ บันทึกคะแนน | เดือน 1–2 | Unit Test ผ่าน 100% |
| ระบบออกรายงาน + ทั้งระบบเชื่อมกัน | เดือน 3 | Integration และ System Test ผ่านทั้ง 26 use case |
| ระบบพร้อมใช้งาน | เดือน 4 | Load Test ได้ตามเป้าหมายเวลา · ครูทำ UAT ได้ครบตาม Persona |

**ภาพ:** ไม่มี

**พูด:** ทุกแถวมาจาก H5 และ H6 · ขอให้กรรมการใช้ตารางนี้ติดตามความคืบหน้าในการนำเสนอทุก 2 สัปดาห์
