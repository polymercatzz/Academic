# A. ที่มาและปัญหา

## A1. ปัญหา

**หัวสไลด์:** งานวิชาการยังพึ่งการทำด้วยมือ และข้อมูลแต่ละงานไม่เชื่อมกัน

**บนสไลด์**

1. **จัดตารางสอนใน Excel** ต้องดูเวลาว่างครู ห้อง ตารางนักเรียน และจำนวนคาบพร้อมกัน แล้วตรวจความถูกต้องเอง
2. **ข้อมูลกระจายหลายที่** ครูกรอกคะแนนในไฟล์ของตัวเองหรือในกระดาษ รายชื่อ คะแนน และตารางสอนอยู่คนละที่ จึงเสี่ยงข้อมูลหาย และข้อมูลไม่ตรงกันเมื่อนำมารวม
3. **ประมวลผลล่าช้า** รวมคะแนนและตัดสินผลการเรียนด้วยมือหรือกึ่งอัตโนมัติ งานค้างช่วงสิ้นภาค
4. **กรอกข้อมูลเดิมซ้ำหลายรอบ** ข้อมูลที่มีในไฟล์อยู่แล้วนำเข้าระบบได้น้อยหรือยุ่งยาก ครูต้องพิมพ์ใหม่ทีละช่อง
5. **หาข้อมูลและติดตามงานช้า** ฝ่ายวิชาการติดตามงานของหลายห้องพร้อมกันได้ยาก
6. **งานซ้ำที่ต้องทำด้วยมือ** ครูผู้สอนทำงานเดิมทุกวัน เช่น เช็คชื่อ นับเวลาเรียน และรวมคะแนนเอง

**ภาพ:** ไม่มี หรือภาพตารางสอน Excel ของจริงถ้าหาได้

**พูด**
- ข้อ 1–4 มาจากที่มาและความสำคัญ (บท 1.1) · ข้อ 5–6 มาจากปัญหาของผู้ใช้ 2 บทบาท (Persona ข้อ 3.1.1) ซึ่งเล่าต่อในสไลด์ Persona
- ข้อ 1 คืองานที่ซับซ้อนที่สุด จึงเป็นจุดเด่นของโครงงาน

**ระบบลดงานซ้ำ** — ตอบปัญหาข้อ 2, 4, 5

- งานที่ใช้เวลานาน (จัดตาราง คำนวณผลทั้งระดับ นำเข้าไฟล์) ระบบทำเบื้องหลัง ผู้ใช้ไม่ต้องรอหน้าจอ

## A3. Actor และ Persona

**หัวสไลด์:** ระบบมีผู้ใช้ 2 บทบาท ครูผู้สอนใช้งานทุกวัน ส่วนครูฝ่ายวิชาการเป็นผู้จัดการและอนุมัติ

**บนสไลด์** (2 คอลัมน์ คอลัมน์ละ 1 คน)

| | อ.สุนิสา ปัญญาดี | ครูสมศรี ใจดี |
|---|---|---|
| ตำแหน่ง | หัวหน้างานวิชาการ | ครูคณิตศาสตร์ · ครูประจำชั้น ม.2/1 · กรรมการฝ่ายวิชาการ |
| ป้าย Actor | **ครูฝ่ายวิชาการ** | **ครูผู้สอน** (+ ฝ่ายวิชาการ) |
| หน้าที่ในระบบ | • จัดการหลักสูตรและรายวิชา<br>• จัดและเผยแพร่ตารางสอน<br>• พิจารณาคำร้องและเวลาไม่ว่าง<br>• ตรวจ อนุมัติ หรือตีกลับผลการเรียน | • เช็คชื่อรายคาบทุกวัน<br>• ดูตารางสอน กรอกเวลาไม่ว่าง ยื่นคำร้อง<br>• ตั้งโครงสร้างคะแนน กรอกคะแนน ส่งผล<br>• ขอปลดล็อก บันทึกสอบซ่อม |
| ปัญหาที่เจอ | • ทุกหน้าต้องเลือกปี ภาค ชั้น ห้องใหม่<br>• รายงานเป็นตารางใหญ่ เรียงหรือกรองไม่ได้<br>• ไม่รู้ว่าคาบไหนยังไม่เช็คชื่อ | • ตรวจว่าเช็คชื่อครบต้องตั้งตัวกรองทุกครั้ง<br>• คะแนนเก็บอยู่หลายไฟล์<br>• ต้องรวมคะแนนและตรวจเองก่อนส่งผล |
| คำพูด | "อยากรู้ทันทีว่าห้องไหนยังมีปัญหา" | "อยากกรอกคะแนนครั้งเดียว แล้วส่งผลได้เลย" |

ใต้คอลัมน์ซ้าย 1 บรรทัด: ดูคะแนนได้ทุกห้อง แต่**แก้คะแนนไม่ได้**

**แถบล่าง**
- บทบาทย่อยของครูผู้สอน (ไม่ใช่ Actor แยก): **ครูประจำชั้น** ดูการเข้าเรียนของห้องตนทุกวิชา · **ครูที่ปรึกษาชุมนุม** บันทึกผล ผ/มผ
- ผู้ที่ไม่ได้ใช้ระบบโดยตรง: นักเรียน (เป็นข้อมูล) · ผู้อำนวยการ (นอกขอบเขต) · บัญชีผู้ใช้และสิทธิ์อยู่ที่ Service B

**ภาพ:** crop เฉพาะรูปถ่ายจาก `docs/persona/persona-sunisa.png` และ `docs/persona/persona-somsri.png` (รูป 3.1, 3.2) · ปัญหาและคำพูดย่อจากกล่อง "ปัญหาในระบบเดิม" ในรูปเดียวกัน

**พูด**
- Persona 1 คนแทน 1 บทบาท (ข้อ 3.1.1) · ปัญหาของ 2 คนนี้คือที่มาของปัญหาข้อ 5–6 ในสไลด์ A1
- ความต้องการที่มาจาก Persona (ถ้ากรรมการถาม ชี้ต่อไปที่ Functional Requirements ข้อ 3.1.3)
  - อ.สุนิสา: ตรวจการชนของตารางสอน · พิจารณาคำร้อง · ตรวจและอนุมัติผลการเรียน · รายงานสรุป
  - ครูสมศรี: ดูตารางสอนรายบุคคล · คำนวณคะแนนและเกรดอัตโนมัติ · นำเข้าคะแนนจากไฟล์ · เช็คชื่อรายคาบ
- ครูสมศรีมีหลายบทบาทในคนเดียว ระบบจึงให้สลับบทบาทได้ ถ้าตรวจห้องที่ตนสอน ระบบติดป้าย "ตรวจงานตนเอง"
- Persona สร้างจากการวิเคราะห์ระบบเดิม ยังไม่ใช่ผลสัมภาษณ์ (ถ้ากรรมการถาม)

## A4. ขอบเขตระบบ

**หัวสไลด์:** ทีมรับผิดชอบ 5 ระบบย่อยงานวิชาการ ส่วนบัญชีผู้ใช้และสิทธิ์อยู่ที่ Service B ของอีกทีม

**บนสไลด์** (5 กล่องเรียงตามลำดับใช้งานในหนึ่งภาค)

| ระบบย่อย | ขอบเขต |
|---|---|
| 1. จัดการหลักสูตร | หลักสูตร แผนการเรียน (เช่น วิทย์–คณิต, ศิลป์) รายวิชาพื้นฐานและเพิ่มเติม มอบหมายครูผู้สอน |
| 2. จัดตารางสอน | จัดได้ 3 วิธี · ตรวจการชนครูและห้องทุกครั้งที่แก้ · เผยแพร่รายห้องและรายครู · คำร้องขอเปลี่ยน · เวลาไม่ว่างของครู |
| 3. เช็คชื่อ | เช็ครายคาบ (มา สาย ลา ขาด) · สรุปเวลาเรียน · มส เมื่อต่ำกว่าร้อยละ 80 · ปลด มส |
| 4. บันทึกคะแนน | คะแนนเก็บ กลางภาค ปลายภาค · คุณลักษณะฯ · อ่าน คิดวิเคราะห์ เขียน · ชุมนุม ผ/มผ |
| 5. ออกรายงาน | ผลการเรียน คะแนนเฉลี่ย การเข้าเรียน นักเรียนไม่ผ่านเกณฑ์และสอบซ่อม · ส่งออก Excel / PDF |

**นอกขอบเขต** (กล่องเทาด้านข้าง): บัญชีผู้ใช้และสิทธิ์ (Service B) · ระบบแจ้งลาของนักเรียน · งานบุคลากร · ความประพฤติ

**ขอบเขตอื่น** (บรรทัดเดียว): ใช้ผ่านเว็บเบราว์เซอร์ · PostgreSQL · งานที่ใช้เวลานานทำเบื้องหลังผ่าน Task Queue · ยืนยันตัวตนผ่าน Service B ทาง API Gateway

**พูด:** เทอม 1 คือวิเคราะห์ ออกแบบ และต้นแบบหน้าจอ (HTML + JS) ส่วนพัฒนาและทดสอบระบบจริงทำในเทอม 2

## B3. Tech stack

**หัวสไลด์:** ใช้ Next.js กับ FastAPI บน PostgreSQL และแยกงานที่ใช้เวลานานไปให้ Celery

**บนสไลด์** (จัดเป็นชั้น บนลงล่าง)

| ชั้น | เทคโนโลยี | ใช้ทำอะไร |
|---|---|---|
| Frontend | **React + Next.js** | Unified Web Portal รวมหน้าจอทุกระบบ · หน้าลากวางตารางสอน และกรอกคะแนนจำนวนมาก |
| API Gateway | **Nginx** | จุดรับคำขอเดียว ส่งต่อตามเส้นทาง |
| Backend | **FastAPI** (Python) + Pydantic | RESTful API · ตรวจข้อมูล · สร้างเอกสาร OpenAPI ให้ตกลงกับทีม B ได้ง่าย |
| ORM | **SQLAlchemy** + migration | เขียน query ด้วย Python · async ผ่าน asyncpg |
| Database | **PostgreSQL** | ACID · ใช้ร่วมกับทีมอื่นแต่แยก schema (`academic`) · ออกแบบตาม 3NF |
| งานเบื้องหลัง | **Redis + Celery** | Redis เป็นคิว · Celery Worker จัดตารางอัตโนมัติ คำนวณผลการเรียน นำเข้าคะแนน |
| Deploy | **Docker** | Service A, Redis, Celery Worker แยก container |

**ต้นแบบเทอม 1:** HTML + JavaScript + ข้อมูลจำลอง (JSON / localStorage)

**พูด:** เลือกแบบ Microservice เพราะต้องทำงานร่วมกับอีก 2 ทีมผ่าน API

## B4. Architecture

**หัวสไลด์:** ระบบงานวิชาการ (Service A) เป็นหนึ่งในสาม service หลัง Nginx

### B4.1 ภาพรวมทั้งโรงเรียน (รูป 3.3)

**บนสไลด์:** รูป 3.3 เน้นสี Service A

```
ผู้ใช้ (ครูฝ่ายวิชาการ · ครูผู้สอน · ครูประจำชั้น · นักเรียน · ผู้ปกครอง)
        │
Unified Web Portal (Next.js)
        │
Nginx (API Gateway)
 ├─ /api/academic  → Service A ระบบงานวิชาการ  ← โครงงานนี้
 ├─ /api/admission → Service B งานทะเบียน + IAM (เข้าสู่ระบบ, ข้อมูลหลัก)
 └─ /api/support   → Service C งานแนะแนว
        │
PostgreSQL (แยก schema ต่อระบบ) · Redis + Celery (ใช้ร่วมกัน)
```

**ภาพ:** `docs/architecture/system-architecture-school.png`

**พูด:** ทั้ง 3 service ใช้ FastAPI ใน Docker · Service A เรียก Service B เพื่อยืนยันสิทธิ์และขอข้อมูลหลัก · MinIO มีในภาพแต่ระบบนี้ไม่ได้ใช้

### B4.2 ภายใน Service A (รูป 3.4)

**หัวสไลด์:** ทุกคำขอผ่านการตรวจสิทธิ์ก่อน แล้วทุกระบบย่อยใช้ชั้นกฎร่วมกัน

**บนสไลด์**

```
คำขอจาก Nginx
  → ตรวจ Token + บทบาท
  → API ของ 5 ระบบย่อย (หลักสูตร · ตารางสอน · เช็คชื่อ · คะแนน · รายงาน)
  → ชั้นกฎร่วม (ตรวจการชน · คำนวณผลการเรียน · ควบคุมสถานะข้อมูล)
  → Repository → PostgreSQL
  งานนาน → คิว Redis → Celery Worker
          (จัดตารางอัตโนมัติ · คำนวณผลการเรียน · นำเข้าคะแนนจากไฟล์)
```

**ภาพ:** `docs/architecture/system-architecture.png`

**พูด:** สถาปัตยกรรมในรูป 3.3 และ 3.4 คือเป้าหมายของเทอม 2 ต้นแบบเทอม 1 ยังเป็นหน้าจออย่างเดียว

## B5. การไหลของข้อมูล

**หัวสไลด์:** ข้อมูลไหลจากหลักสูตรไปถึงรายงานโดยครูไม่ต้องกรอกซ้ำ

**บนสไลด์** (ลูกศรแถวเดียว ซ้ายไปขวา)

```
หลักสูตร ──▶ ตารางสอน ──▶ เช็คชื่อ ──▶ บันทึกคะแนน ──▶ รายงาน
```

| จาก → ไป | ส่งอะไรต่อ |
|---|---|
| หลักสูตร → ตารางสอน | รายวิชาในแผนการเรียน ห้องที่สอน และครูผู้สอน → นำไปจัดเป็นคาบ |
| ตารางสอน → เช็คชื่อ | คาบในตารางที่**เผยแพร่แล้ว** = คาบที่ต้องเช็คชื่อ |
| เช็คชื่อ → บันทึกคะแนน | เวลาเรียนและผล มส → ใช้ตัดสินผลการเรียน |
| บันทึกคะแนน → รายงาน | ผลการเรียนที่ฝ่ายวิชาการ**อนุมัติแล้ว** |

แถบล่าง "ข้อมูลหลักใช้ร่วมทุกระบบ": ปีการศึกษาและภาคเรียน · ระดับชั้น · กลุ่มสาระ · นักเรียนและห้องเรียน · ครูประจำชั้น

**ภาพ:** `docs/architecture/module-flow.png` (รูป 3.5)

**พูด:** ลำดับนี้คือลำดับการใช้งานในหนึ่งภาคเรียน และเป็นลำดับพัฒนาในเทอม 2 ด้วย
