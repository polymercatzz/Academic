# แผนบทที่ 4 และบทที่ 5

> ร่างวันที่ 2026-11-05 · ต่อจาก [report-plan.md](report-plan.md) (ระยะ 5 และ 6) · ขอบเขตอ้างจาก [scope-ch3.md](scope-ch3.md)
> ข้อตกลงเดิมที่ยังใช้อยู่: บท 4 เป็นภาพหน้าจอเดโม ไม่มีผลการทดสอบ · การทดสอบทั้งหมดย้ายไปแผนในอนาคตของบท 5

ชื่อบทตามคู่มือ (Rule §3) คือ บท 4 "ผลการทดลอง / ระบบต้นแบบ" และบท 5 "วิเคราะห์และสรุปผล" งานนี้ไม่มีการทดลอง จึงเสนอให้ใช้ชื่อ **บทที่ 4 ระบบต้นแบบ** และ **บทที่ 5 สรุปผลและข้อเสนอแนะ** ต้องคุยกับอาจารย์ที่ปรึกษาก่อนว่าใช้ชื่อนี้ได้

## บทที่ 4 ระบบต้นแบบ

แนวคิดของบทนี้: ผู้อ่านต้องเห็นว่า**ขอบเขตในบท 3 ทุกข้อมีหน้าจอรองรับ** จึงเรียงหัวข้อตามระบบย่อยใน scope-ch3.md และให้ทุกภาพอ้างเลข UC

### 4.1 เครื่องมือและสภาพแวดล้อมที่ใช้พัฒนาระบบต้นแบบ

- ภาษาและไลบรารี: HTML, CSS, JavaScript, Tailwind CSS, Chart.js
- การเก็บข้อมูล: ข้อมูลจำลองใน JSON / JS และ `localStorage` ของเบราว์เซอร์ (ยังไม่มีฐานข้อมูลจริง) — ดู [data.md](data.md)
- วิธีเปิดใช้งาน: `python3 -m http.server`
- บอกตรง ๆ ว่าระบบต้นแบบเป็น**ต้นแบบหน้าจอ (front-end prototype)** ส่วนฐานข้อมูลออกแบบไว้ในบท 3 แต่ยังไม่ได้เชื่อม เพื่อไม่ให้กรรมการถามว่าข้อมูลบันทึกที่ไหน

### 4.2 โครงสร้างหน้าจอและเมนูตามบทบาท

- **รูป** แผนผังหน้าจอ (sitemap) แยกเมนู ครูฝ่ายวิชาการ / ครูผู้สอน — วาดใหม่ใน draw.io จากตารางใน [modules.md](modules.md)
- **รูป** ส่วนประกอบหลักของหน้าจอ (sidebar, header, chip ขอบเขตข้อมูล, ตัวสลับบทบาท)
- อธิบายการสลับบทบาทของผู้ใช้ที่มีสองบทบาท (grading ADR 0003)

### 4.3 ข้อมูลและผู้ใช้ที่ใช้สาธิต

- ตาราง persona: อ.สุนิสา (ครูฝ่ายวิชาการ), ครูสมศรี (ครูผู้สอน + ครูประจำชั้น ม.2/1 + ฝ่ายวิชาการ) — จาก [personas.md](personas.md)
- ขนาดข้อมูลจำลอง เช่น ม.1–ม.3 × 3 ห้อง × 9 วิชา ครู 26 คน
- ⚠️ ก่อนแคปต้องแก้ให้ persona ตรงกันทุกโมดูล (ตอนนี้ตารางสอนใช้ อ.อนุชา ส่วน grading ใช้ครูสมศรี) ไม่อย่างนั้นภาพข้ามบทจะคนละคน

## บทที่ 5 สรุปผลและข้อเสนอแนะ

### 5.1 สรุปผลการดำเนินงาน

- **ตาราง** วัตถุประสงค์ข้อ 1.2 ทีละข้อ · ผลที่ได้ · หลักฐาน (เลขรูป / ตาราง) · ทำได้ / ทำได้บางส่วน
- สรุปตัวเลขของงาน: 17 FR, 26 UC, 6 Activity Diagram, ER 59 ตาราง, หน้าจอ N หน้า

### 5.2 ผลการแก้ปัญหาของระบบเดิม

- **ตาราง** ปัญหา P1–P9 → แนวทาง → สถานะในระบบต้นแบบ (✅ / 🟡) — ข้อมูลพร้อมแล้วใน [pain-points.md](pain-points.md#สถานะในระบบใหม่)
- เทียบกับตารางที่ 3.1 (ปัญหาของระบบที่เกี่ยวข้อง) ว่าแต่ละข้อแก้ด้วยหน้าจอใด

### 5.3 จุดเด่นของระบบ

เทียบกับตารางที่ 2.3 (SchoolBright, SGS, aSc) เช่น

- ตรวจการชนด้วยเวลาจริง รองรับโครงสร้างเวลาต่างกันตามช่วงชั้น (timetable ADR 0002)
- ตารางฉบับเผยแพร่แก้ไม่ได้ มีประวัติฉบับ และขั้นตอนคำร้องขอเปลี่ยน (timetable ADR 0001)
- ขั้นตอนส่งผล → ตรวจ → ตีกลับพร้อมหมุดข้อสังเกต → อนุมัติ โดยฝ่ายวิชาการแก้คะแนนแทนครูไม่ได้ (grading ADR 0001, 0002, 0006)
- เวลาเรียนจากการเช็คชื่อกำหนดสถานะ มส ได้เอง (grading ADR 0011)
- ผู้ใช้คนเดียวมีหลายบทบาท สลับมุมมองได้

### 5.4 ปัญหาและอุปสรรค

- ขอบเขตเปลี่ยนระหว่างทำ (เพิ่มเช็คชื่อ ชุมนุม คุณลักษณะฯ เมื่อ 2026-11-04; ตัด UC ส่งออก)
- ไม่ได้สัมภาษณ์ผู้ใช้จริงโดยตรง ปัญหาระบบเดิมมาจากการวิเคราะห์ของทีม
- แต่ละโมดูลพัฒนาแยกกัน ข้อมูลจำลองและ persona จึงไม่เชื่อมกัน ([data.md](data.md#จุดที่ยังไม่เชื่อมกัน))
- ต้องพึ่งระบบของอีกทีม (User Management Service) ที่ยังไม่พร้อม

### 5.5 ข้อจำกัดของระบบต้นแบบ

- ไม่มี back-end และฐานข้อมูลจริง ข้อมูลอยู่ในเบราว์เซอร์ รีโหลดบางหน้าแล้วหาย (หลักสูตร)
- การบังคับสิทธิ์มีแค่ระดับเมนู เปิด URL ตรงยังเข้าได้
- ปุ่มส่งออก PDF/Excel เป็นแบบจำลอง (P5, P6)

### 5.6 ข้อเสนอแนะและแผนในอนาคต

1. พัฒนา back-end และฐานข้อมูล PostgreSQL ตาม ER ในบท 3 พร้อมตารางที่ยังขาด: งานเบื้องหลัง (Task Queue), log การนำเข้าไฟล์, ประวัติการแก้ไขหลักสูตร ([report-plan.md](report-plan.md#เรื่องที่ต้องตัดสินภายหลัง))
2. เชื่อมต่อ User Management Service และระบบข้อมูลหลักของอีกทีม แล้วบังคับสิทธิ์ที่ฝั่งเซิร์ฟเวอร์
3. การทดสอบ (ย้ายมาจากข้อ 1.4): Unit Test ของการคำนวณคะแนน/เกรด/มส/Conflict · Integration Test กับระบบของอีกทีม · UAT กับครูและฝ่ายวิชาการจริง · Load Testing ตอนจัดตารางอัตโนมัติและคำนวณเกรดทั้งโรงเรียน
4. สร้างไฟล์ PDF/Excel จริง
5. ขยายนอกขอบเขตข้อ 1.3.4: ขั้นอนุมัติของผู้อำนวยการ · หน้าจอนักเรียน/ผู้ปกครอง · ระบบแจ้งลาโดยครูประจำชั้น
